`ArgumentContext` 是 env 的唯一形态：字段数 **不超过 64** 的**扁平**映射（SEC-07）。它在构造期把键值对拷进不可变视图，构造完成后不可变——这样 `01-CONTEXT.md` §7 要求的「每次决策新建 env」不会退化成一个可变映射被多个线程共享。值类型限定为标量与字符串，**不接受任意对象**：`ArgumentContext` 不提供 `Object` 值的构造重载，因此业务对象图在类型上就进不来（`01-CONTEXT.md` §7 硬禁止，SEC-07 的 Secure Behavior 明确「业务对象图不入 env」）。字段数超 64 直接抛 `WhitelistViolationException`。

**每条能力各自的变量集大小上限**（`01-CONTEXT.md:146` §6 开放项 2 要求「每条能力变量集大小的**上限**，并纳入 `EXPR-04` JMH 基准」——注意这条**不是**「数据线注册表形态」，后者是 `01-03` 的工作；依据 `01-RESEARCH.md:490-491` D.2）：§2.3 表格的当前字段数为 `RATE_LIMIT` 7、`CANARY` 5、`CACHE` 3，据此选定带余量的**按能力上限**——`RATE_LIMIT` ≤ 16、`CANARY` ≤ 8、`CACHE` ≤ 8，三者都不超过全局 64 预投影上限（SEC-07）。**这三个数是暂定值，不是定论**：`01-RESEARCH.md:491` 要求 JMH 在 8 / 16 / 32 / 64 个变量下测求值 p99、找出拐点后把上限**钉在拐点之下**，该 env-size 扫描维度在 `01-08` 的 `ExpressionEvalBenchmark` 中实现（EXPR-04）。若实测拐点低于 16 / 8 / 8，对应上限必须**下调**；执行者不得因为某个上限「看起来还有余量」而保留高于拐点的值。超限按 deny-by-default 处置：抛 `WhitelistViolationException`，不截断。

`ArgumentSource` 是从调用方对象**反射展开**出标量的适配层。取值方式为**反射 + 递归展开 + 白名单**，是 `01-CONTEXT.md` §2.3 **用户已选定**的方案（`01-DISCUSS-CHECKPOINT.json:246-260` 记录了两个分支，反射被标为 mandatory；§2.3「被否」条目里的「不反射的显式 context」是被否方案，不是本计划采用的形态）。业务代码因此**无需逐字段构造 context**——这正是选反射要付出的代价被接受的原因。

**「业务对象图不入 env」的保证如何与反射并存**（这一条最容易被写歪，必须说清）：保证的对象是 **env 的存储形态**，不是「SDK 是否读取过对象图」。`ArgumentSource` 读取并**展开**对象图，但只把**展开后的标量**放进 `ArgumentContext`；展开过程不保留任何对象引用——图是被**展开**，不是被**存进** env。业务对象图进不来 env，靠的是三件事的合力：只放标量（`ArgumentContext` 无 `Object` 值构造重载，类型上就进不来）、≤64 上限、以及按能力分段的 allow 名单。写法上不要把它表述成「SDK 不读取对象图」——那是反射路径的否定式描述，且会让 `01-CONTEXT.md:134` 的 EXPR-11 断言（敏感字段在**任何反射展开路径**下不可进入 env）失去被测对象。

**§6 开放项 3 的四个设计要素**（`01-CONTEXT.md:147`；依据 `01-RESEARCH.md:493-498` D.3）：

- **深度上限**：`SandboxPolicy.depth`，**默认 2、硬上界 3**。按深度**递归展开**嵌套对象（public getter / 顶层 public 字段；`Map` 展开、`Collection` 不展开），到达上界即停并把剩余层标记为未展开。默认取 2 而非 1：限流与灰度的 env 常含一层嵌套（如 `card.risk.band`），`depth = 1` 会让这类规则**恒定落空**——不是报错而是静默取不到值，正是 §2.3 点名要拒绝的静默失效点。`ARCHITECTURE.md:317` 的扁平 `Map` 是**投影产物**，不构成「调用方传参必然扁平」的约束，不能据此把上界压回 1。硬上界 3 是性能与逃逸面双约束：每多一层就多一份反射开销，且多一个可被用来搭引用链的对象；3 层已覆盖现有全部数据线，突破需独立论证 + 新一轮压测（`01-08` env-size 扫描）。**每层都独立跑 deny 判定**——嵌套深处的强敏感字段与顶层同等对待，不因「藏在二层」而漏检。
- **集合 / `Map` 展开策略**：**只展开 `Map<String, ?>`**（取 `get`），**不展开 `Collection`**。理由是 `Collection` 的元素类型不确定，无法静态纳入白名单；且 `list.size()` 在 `01-RESEARCH.md:302` 矩阵第 1 类已被沙箱拒绝，把它放进 env 白名单会与攻击矩阵自相矛盾。`Map` 的 key 参与 env 命名，因此 key 与 value 同样要走 deny 判定（见下）。
- **循环引用保护**：深度 > 1 后循环引用在结构上**可能**发生（`a.self == a`），因此用 `IdentityHashMap<Object, Boolean>` 维护**当前递归路径**上的已访问实例集合：进入任一实例前检查、离开后从路径中移除。必须用 `IdentityHashMap` 而非 `HashMap`——`equals`/`hashCode` 可被规则数据里的值对象覆写，用它们做身份判定会把两个**不同**实例误判为同一个（或漏判真回指），这既是正确性缺陷也是一条绕过 deny 的路径。必须是**路径集合**而非全局集合：同一实例在两条不同分支上各出现一次是合法数据，只有沿**同一条路径**回指才是循环。命中回指时停止展开该分支（不抛异常，字段缺席由既有 nil 语义处理），并计入一个展开截断计数。
- **反射元数据缓存结构**：`MethodHandle` 缓存**必须有界**（`PERF-04`）。采用**启动期一次性构建的不可变快照** `Map<Class, MethodHandle[]>`（`MethodHandles.publicLookup()`，**只用 public getter**，不碰私有字段），理由是反射元数据不随业务数据变化，可以在冷启动期构建完毕，因此**热路径不做缓存查找**——`01-CONTEXT.md:317` / `ARCHITECTURE.md` 记录的「不缓存必击穿 P99」正是这条的理由。缓存以 `Class` 为键有界：`Class` 只来自调用方实际传入的根对象及其展开到的类型，**不得**对任意类名做反射解析（那等于开放任意类加载），类型集合在启动期快照后即固定。

**deny 判定跑在反射展开路径上**（INV-8 的落点，也是 `01-CONTEXT.md:134` EXPR-11 断言「在任何反射展开路径下」的兑现）：判定发生在**展开的每一步、把值放进 `ArgumentContext` 之前**——顶层字段名、getter 派生名、以及 `Map` 的 key 都要过 deny 名单。因此一个埋在业务对象里任意**可达**位置的 `cvv` 字段（顶层字段、嵌套 getter 的返回值、或 `Map` 的 key）在被展开到 env 的那一刻就被 `WhitelistViolationException` 拒绝，不会先进入 env 再被清理。深度上限之外的位置根本不会被展开，也就无从进入 env——这条保证对未展开位置同样成立，方式是「不被展开」而不是「被拒绝」，两者都不产生入 env 的可能。

`EvalContextWhitelist` 从 `env-whitelist.json` 加载两级名单：
- **允许清单（按能力分）**：表达式里可以引用的变量名，**按能力段各有一份**（INV-7：「env 变量集 SDK 侧固定、按能力分；规则不声明变量」）。`01-CONTEXT.md` §2.3 规定白名单外变量名使规则**拒绝加载**——这发生在 `01-03` 校验阶段，本计划提供按能力分组的名单与判定入口，由 `01-03` 的 `RuleValidator` 调用。**不要**做成「加载后在求值时得到 nil」：`01-RESEARCH.md` 的探针记录了属性语法糖关闭后缺失属性返回 nil 的行为，那正是「规则看起来生效了但其实一直在取 nil」这种静默失效的来源。
  **deny-by-default 按能力判定**（INV-10）：判定的是「该变量是否列在**这条规则所属能力段**的清单里」，不是「是否列在全局某处」。因此 `RATE_LIMIT` 规则引用一个只有 `CANARY` 才有的变量，是**加载期拒绝**，不是求值期拿到 nil——它与「引用全局不存在的变量」是同一种失败，处置也相同（整段拒绝 + 计数告警）。这条边界不能退化成「先查全局并集」的实现。
- **强敏感字段 deny 名单**：完整卡号、CVV、持卡人姓名、有效期四类（`01-CONTEXT.md` §7 与 PCI 红线）。**四类而非三类**：`01-CONTEXT.md:134` 的 §5 门 EXPR-11 点名断言的是 `cvv` / `pan` / `expDate` / `cardHolderName` **四个**标识符，而 §2.3 的三层分级只列了三类（未含 `expDate`）。两处对不上时以**更严**的一侧为准：把有效期也放进 deny 名单，既满足 §5 门的四个断言点，又不违反 §2.3（「强敏感永不进 env」是禁止性规定，多禁一类不与它冲突）。**有效期不是新增 env 变量**——它只出现在 deny 名单里，`01-CONTEXT.md` §2.3 的字段表不因此多出任何一行。这三类**即使调用方主动放入** `ArgumentContext` 也要被拒绝——deny 优先于 allow。这与 OBS-07 是同一族的纪律：可追溯性或便利性都不构成放宽的理由。deny 名单用**语义判定**（字段名归一化后匹配卡号 / cvv / cvv2 / 持卡人 / holder / name 等形态），因为 PCI 关注的是数据类别而不是具体列名；归一化规则写在资源文件里，改规则不改代码。
