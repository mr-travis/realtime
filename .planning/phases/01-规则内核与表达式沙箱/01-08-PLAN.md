**tag 白名单与 env 分级是两套判定，这是本任务最关键的一条。** `01-CONTEXT.md` §3 的敏感字段三层分级管的是**进 env 的资格**：①公开（`channel` / `cardProduct` / `dataLine` / `cardBin`）明文进 env；②业务标识（`merchantId` / `issuerId` / `subjectHash` / `keyHash`）明文进 env 但**禁止做指标标签**（Out of Scope 第 10 条）；③强敏感永不进 env。但「不敏感」不等于「适合做 tag」——tag 的约束是**基数**，不是敏感性。`cardBin` 是最典型的反例：`01-VALIDATION.md:127` 明确生产规模是 **10 万卡 BIN 基数**，把 `cardBin` 当 tag 会直接制造 10 万条 series，再乘上其他 tag 就是基数爆炸。所以 `TagAllowlist` 是一份**独立于三层的、更严的**白名单：只收取值集合封闭的键（`dataLine` / `cardProduct` / `channel` / `ruleId`），**明确排除** `cardBin`（基数随接入方数据规模变化，不封闭）与 `ruleVersion`（无界——推送次数没有上限，`01-CONTEXT.md` §7 已把「无界 ruleVersion」列为硬禁止）。`ruleId` 可以进 tag，因为它的基数上界就是规则数，而 `01-05` 已用 `RoutePlanSizeTest` 钉住「路由表条目数 == 规则数」。

`TagAllowlist` 是 **deny-by-default**：未在白名单内的键一律拒绝，不接受「先放行再说」。这与 `01-07` 的脱敏策略同族纪律，两者在语义上一致（默认拒绝）而不是相反——这是刻意的，因为「默认放行」在 tag 场景下的后果是 Prometheus 侧的静默基数爆炸，而爆炸之后的清理是手工的。

`PreRegisteredSeries` 落实 OBS-09 的**有界 tag 预注册**：所有合法的 tag 键取值组合在初始化时从封闭枚举**穷举**并预创建，热路径只做一次数组 / 查表取用，**从不**在决策路径上按动态 tag 调用「取或建」。这是一个刻意的结构性选择：Micrometer 的 `registry.counter(name, tags)` 会在 tag 组合不存在时**自动创建**新 series——那正是不可逆基数增长的机制。预注册把这个「自动创建」从热路径彻底移除。因此遇到未预注册的组合时不新建 series，而是落到一个有界的兜底 series 并计数——计数不可省（`01-CONTEXT.md` §7 禁止静默失效），但**兜底不新建**是硬要求。

`MetricsPort` 是 SDK 内的窄接口（计数 / 计时），`foundation-core` 只依赖它。Micrometer 与 Prometheus registry 的具体类型只出现在 `foundation-autoconfigure`（Task 2），保持 `01-01` 建立的「数据面模块不依赖 Spring」纪律，同时让本任务的测试可以用一个**记录型**替身直接数 series——这比对着真实 registry 断言更直接：真实 registry 需要 scrape 才看得见，而记录型替身让「新建了几条 series」成为一个可数事实。

**三个独立决策计数器**（`01-CONTEXT.md:96-97` INV-11 / INV-12；`01-CONTEXT.md:136` §5 门「独立计数器测试」；`01-CONTEXT.md:152` §6 开放项 8 要求给出**名称与维度 + 与 meter 契约的对应**）。三者是**三个独立 meter**，不是一个 meter 上的三个 `outcome` 取值——`01-RESEARCH.md` 指标表原写法 `foundation.expression.evaluation{outcome}` 把它们并进了一个 meter 的 `outcome` 维度，那**不满足** INV-11/INV-12：「可分别观测」要求它们能被**各自独立地取数、独立地告警**，共用一个 meter 就做不到（取数要按 tag 拆、告警要按 tag 拆，等于把独立性建立在 tag 约定上而不是 meter 契约上）。`DecisionOutcomeCounters` 落三个计数器：

| 计数器 | 触发时机 | 维度 | 段处置 |
|---|---|---|---|
| `expression_targeting_miss` | 白名单内的变量本次未提供 → nil → 未命中 | `ruleId`、`capability` | 段不回滚（复用 `CAN-09` 语义） |
| `expression_not_match` | 表达式正常求值，结果为 false | `ruleId`、`capability` | 段不回滚 |
| `expression_eval_failed` | 求值失败（nil 运算 / 类型不匹配 / 步数耗尽）并按 `failStrategy` 返回 | `ruleId`、`capability`、`failStrategy` | 段不回滚，走 fail 策略 |

`ruleId` 维度是 INV-11 明文要求的下钻维度（「可按 `ruleId` 下钻」），它在 `TagAllowlist` 里已被判为合格 tag（上界是规则数，`01-05` 已用 `RoutePlanSizeTest` 钉住）。第三个计数器额外带 `failStrategy`——`RL-21` 要求实际生效的 `failStrategy` 记入 `DecisionRecord`，指标侧带同一维度才能把「哪条 fail 策略在生效」与「失败量」对上；取值限于 `RL-17` / `CAN-06` 规定的封闭集合。

**`ruleId` 维度的注册与注销**（OBS-09 的一致性要求，最易漏）：这三个 meter 的 `ruleId` tag 值在规则被**接纳时注册**，在规则被**移除时注销**——由 `01-05` 的差量替换（`RoutePlanDiff`）驱动。因此 tag 取值集合的上界是**在用规则数**，而不是累计推送数；若只注册不注销，规则反复替换会让 `ruleId` 维度无界增长，基数保护形同虚设。注销后不再有新的 series 产生，既有 series 由 registry 的常规生命周期回收。`capability` 与 `failStrategy` 是封闭枚举，随预注册穷举。

三者与 `sandbox_violation`（Task 4）**互不合并**：`sandbox_violation` 是编译期拦截，这三个是运行期求值语义，触发时机不同、处置不同（前者整段拒绝、后者段不回滚），且 `sandbox_violation` 的 `class` 取值与三者的 `ruleId` / `capability` 维度**无任何交集**。

**`CacheStats` 指标注册**（GOV-14 的落点，吸收 `01-04` Task 3 的手交）：`01-04` 交出 `CacheStats`（命中 / 未命中 / **淘汰**三项计数）作为信号源。**本任务只消费并验收**，不实现注册——注册动作在 **Task 2** 的 `MicrometerMetricsAdapter` 中完成，落为 `foundation.cache.stats{hit,miss,evict}`，三个取值来自封闭枚举；本任务的验收点是「`CacheStats` 的三项计数能在指标上读到，且与 `CacheStats` 读数相等」。淘汰计数是判断编译缓存「稳态是否真的收敛」的唯一手段——没有它就无法知道容量是否设小了，所以它必须是可取数的指标而不是日志。

`TagAllowlistTest`（SEC-04）断言：(a) PAN / CVV / 完整卡号 / traceId / `ruleVersion` / `cardBin` / 四个业务标识键**逐一被拒绝**，每条独立断言；(b) `cardBin` 被拒绝的理由是基数而非敏感性，测试名与断言信息要写明这个区别（否则后来者会以为「`cardBin` 不敏感所以应该能用」）；(c) 一个从未见过的键名被拒绝（deny-by-default 的真正判据）；(d) 四个合格键通过。
`FoundationMetersTest`（OBS-09）用 `RecordingMetricsPort` 断言：(a) 跑 10 万次取值各异的决策后，series 总数**恒等于**预注册时的组合数（不是大于等于）；(b) 遇到未预注册组合时**不新建** series 且兜底计数递增；(c) 同一组合重复 10 万次只对应一条 series。

**三个独立计数器的可分别观测性**（`01-CONTEXT.md:136` §5 门的直接兑现，并入本测试类以复用本任务的 automated 断言）：核心用例是构造一个**若任意两个被合并就无法区分**的场景——同一条规则、同一能力段、同一 `ruleId`，连续产生「变量缺失未命中」一次、「求值结果为 false」一次、「求值失败按 `failStrategy`」一次。断言三条计数器**各自递增 1**，且 `sandbox_violation` **不**因这三次决策递增（运行期语义不得污染编译期计数）。另加：三条计数器的 `ruleId` tag 值相同而 meter 名不同（证明是三个独立 meter 而非一个 meter 的 tag 组合）；规则移除后该 `ruleId` 不再产生新 series；`expression_eval_failed` 的 `failStrategy` 维度可区分 fail-close 与 fail-open。

`BoundedStructuresTest`（PERF-04）审计 SDK 拥有的全部**长生命周期**结构，证明「远程推送不可无界增堆」。审计对象是四个已被各自计划建立上界的结构，本任务验证它们的**上界在压力下真的成立**（既有测试验证单点性质，本测试验证叠加后的整体）：

1. 旧快照释放（`01-03` 的 `RuleSetSnapshot`）——连续推送 K 份内容各异的规则后，SDK 保留的快照对象数**等于 1**（只有当前生效的那份），不是 K。这条直接对应 T-1-24：旧快照若被链式引用，每次推送就留下一份完整规则集，是最容易被忽略的堆增长源。
2. 编译缓存有界（`01-04` 的 `CompiledExpressionCache`）——容量恒定，淘汰生效。这里要复述 `01-04` 的纪律：**LRU 只是稳态优化，元空间的真正防线是段内规则总数硬上限**；本测试断言 LRU 容量而不把它当作元空间保护，测试名与注释要写明这个区别，否则会被读成「有 LRU 就安全了」。
3. 决策通道有界（`01-07` 的 `RingBufferDecisionSink`）——`DecisionMetrics` 读的是 `RingBufferStats` 的丢弃计数，**不自己维护第二份**。`DecisionMetrics` 里出现一个自己也在计数的丢弃计数器就是两个真相源，会在某一处漏更新。
4. 路由表有界（`01-05`）——条目数 == 规则数，不随运行时长增长。`01-05` 的 `RoutePlanSizeTest` 已覆盖单点，本测试在 10 万 BIN 规模下复核。
5. **求值线程池可关闭**（`01-04` 的 `EvaluationTimeoutPool`，由 `01-04` Task 2 手交）——`BoundedStructuresTest` 在关闭钩子触发后断言**不残留任何非守护线程**，且队列中的待求值任务被**有界地**拒绝而不是无限堆积。线程池是本 SDK 唯一一个自己创建线程的结构：容量有界不等于生命周期有界，一个拒绝关闭的池会在每次热重载时泄漏一批线程，因此它必须进这份审计而不是留在 `01-04` 里自证。

**本任务同时是三个手交信号源的注册点**（三者的实现都不在 `01-08`，只有把信号接到 registry 这一步在这里；漏掉任何一步，信号就是死代码）：

- **`CacheStats` → 缓存指标**（来自 `01-04` Task 3，GOV-14 落点）：注册 `foundation.cache.stats{hit,miss,evict}`，三个取值来自封闭枚举。淘汰计数是判断编译缓存「稳态是否真的收敛」的唯一手段。
- **`DecisionRecord` → trace 导出适配器**（来自 `01-07` 的 `DecisionRecordSink` 与 `01-06` 的 `TraceExporter` 契约）：`DecisionRecord` 里有 `ruleId` / `ruleVersion` / `failStrategy` / `truncated`，而**没有**任何业务标识字段（`01-07` 已保证脱敏）。适配器只把这些字段接到 trace 事件上，**不得**为了「排查方便」把 `cardBin` / `merchantId` 之类加回去——那会绕过 `TagAllowlist` 与脱敏策略，成为一条独立的泄漏路径。断言：导出的 trace 事件字段集合与 `DecisionRecord` 的字段集合**相等**（不多不少），这条相等断言就是「没有偷偷加字段」的证据。
- **三个独立决策计数器**（来自 Task 1 的 `DecisionOutcomeCounters`）：适配器把三个 meter 接到 registry，meter 名与 tag 键一一对应，不合并、不改写维度。

每条断言都用**计数**而非「看起来没涨」：或用反射读取结构尺寸，或用 `RecordingMetricsPort` 计数。`BoundedStructuresTest` 里不出现任何 `assertTrue(size < 1000)` 这类模糊上界——上界要么是 1（快照）、要么是配置的常量（缓存、ring buffer）、要么是规则数（路由表）。

`MicrometerMetricsAdapter` 落在 `foundation-autoconfigure`（`01-01` 已在根 POM 把它列入 `bannedDependencies` 的豁免清单），是 `MetricsPort` 到 Micrometer 的唯一实现。它是**基数的最后一道防线**：即使 `foundation-core` 的预注册被绕过，适配器也只暴露 `PreRegisteredSeries` 已有的 series，不做按 tag 的动态取或建。`foundation-autoconfigure/pom.xml` 追加 `micrometer-registry-prometheus`（版本由 Boot 2.7.6 BOM 管理，**不手写版本号**，`STACK.md` 记录其为 required；`simpleclient_common` 是它的传递依赖，不得单独声明）。若该依赖已由 `01-01` 预声明，则本任务不重复添加——改 POM 前先读，确认后再决定是否需要改动。

适配器不做 `MeterFilter.deny()` 这类「拒绝某个 tag 名」的补救式防护：白名单已经在 `foundation-core` 生效，这里再加一层只是重复。更重要的是，**适配器不吞掉被拒绝的 tag**，它把拒绝计数暴露成指标，这样基数问题在监控上是可见的而不是被静默修剪。

**指标名固定为 `sandbox_violation`**（`01-CONTEXT.md` §2.4 与 §5 EXPR-03 门的原名）。`01-RESEARCH.md` §指标表把它写作 `foundation.sandbox.violation{class}`，这是 Micrometer 命名空间前缀的另一种写法；**本计划以 `sandbox_violation` 为准**，前缀属于 `foundation.` 属性面而非计数器名（属性面由 `01-01` 拥有）。两种写法指同一个计数器，实现时只注册一次，不允许并存两个名字。

**维度只有两个，均为封闭枚举：**
- `class`（逃逸类别）：取下方表格定义的**同一组 12 个值**——`reflection`、`constructor`、`static_method`、`classloader`、`io`、`redos`、`infinite_loop`、`stack_overflow`、`resource_amplification`、`deep_nesting`、`property_syntax`、`env_mutation`。**本行的顺序与取值必须与本任务下方「12 值封闭枚举表」逐条相同**；该表是 `class` 的唯一权威定义，本行只是它的摘要，出现分歧以表为准（旧的 `ast_budget` 命名已废弃，见该表第 9 行）。**不得**由调用方传入自由字符串：类别在 `01-02` 侧就是编译期判定结果，映射到枚举即可，出现枚举外的值是编程错误而非运行时输入。`redos` 对应 EXPR-08 的正则拒绝，`resource_amplification` 对应 EXPR-07 的 AST 节点/长度/深度限额拒绝。
- `capability`（能力段）：取 `01-CONTEXT.md` §3 INV-2 的 `RATE_LIMIT` / `CANARY` / `CACHE` 三值，**不加** ruleId、cardBin、traceId 等任何维度——加了就把基数从固定组合变成随业务量增长，直接违反 OBS-09。**按能力段计数是 INV-2 的要求**（整段拒绝发生在能力段粒度），不是可选维度。

两个维度共 12 × 3 = **36 种固定组合**，全部在 `PreRegisteredSeries` 里预注册；未见组合不新建 series（沿用 Task 1 的纪律）。逃逸企图本身不携带业务标识，因此 `class`/`capability` 两个 tag 都不触碰 §2.3 第二层敏感分级（业务标识禁止做指标标签），无需额外脱敏。

**命名与聚合边界**（`01-CONTEXT.md` §6 开放项 10，本任务必须给出结论，写入 `evidence/sandbox-violation-boundary.md`）：

| 计数器 | 触发时机 | 段处置 | 与 `sandbox_violation` 的关系 |
|---|---|---|---|
| `sandbox_violation{class,capability}` | 编译期沙箱/预算拦截 | 整段拒绝 | 独立计数器，不与下三者合并 |
| 变量缺失未命中 | 变量在白名单内但本次请求未提供 → nil → 不命中 | 段不回滚 | **独立**，**不得**折进 `sandbox_violation` |
| 评估为 false | 表达式正常求值结果为 false | 段不回滚 | **独立** |
| 求值失败（按 fail 策略） | nil 运算 / 类型不匹配 / 步数耗尽 | 段不回滚，走 `failStrategy` | **独立** |

INV-11 / INV-12 要求后三者**各自可独立观测**，因此 `sandbox_violation` 与它们**不共享 tag、不共享 series、不做求和聚合**：前者的 `class` 维度没有任何值会与「变量缺失」「求值为 false」「求值失败」重叠，合并会同时丢掉两边的可诊断性。「求值失败」尤其不能并入——它是运行期 fail-close / fail-open 的依据，量级通常远大于逃逸企图，混在一起会让告警彻底失真。可以做的聚合只有**按 `class` 或按 `capability` 的下钻**（group by 已有 tag），不做跨计数器的合并。

**告警严重度上限（`01-CONTEXT.md` §2.4 末条，已决定）**：`sandbox_violation` 的一次自增**不得**升级为高危（high/critical）安全告警。它走**有界、低严重度**通道——按 `class` 设固定低severity 基线（如 `warning` / `INFO`），且该严重度是**上限**不是默认值：允许运营侧在 `class=reflection` 这类明确探测意图的类别上自行调高，但**SDK 契约与默认值不得暗示高危**。理由（§2.4 原文）：规则作者试错、拷贝外部代码都会触发编译期拦截，全部走高危通道会在数月内被无视，真事件与噪声混同。实现上这条落成一条可测的约束：`MetricsPort` 不得为 `sandbox_violation` 注册任何高严重度告警规则，默认严重度为低。

**SDK 只上报企图，不做成功检测**（INV-15 / §2.4）：`SandboxViolationCounter` 的接口与 Javadoc 都**不得**出现任何判定「沙箱已被突破」的方法、字段或返回值。沙箱被绕过时表达式编译通过、求值通过、返回一个值，攻击者的调用在 SDK 眼里就是一个 boolean——此类判定属进程外（EDR / 子进程与出网监控）。本类的方法名统一为 `recordAttempt(...)`，不用 `recordViolation` / `onEscape` 这类会被读成「事已发生」的措辞。
