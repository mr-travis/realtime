- **上限声明独立成文件**。三个 `.support` 文件内容为形如 `{"maxSupportedVersion": N}` 的小 JSON，与定义文件同目录，使「定义到第几版、支持到第几版」同屏可对。**不得**把上限写成代码常量（跨能力汇总要人工 review），**不得**放在 Spring 配置或 Nacos——`01-CONTEXT.md` §7 明确禁止把 `maxSchemaVersion` 做成运行时可变量：下调上限会让全量实例对已生效规则集整份拒绝，属于自伤。

`SchemaDefinition` 与 `SchemaSupport` 是两个独立的只读值对象；`SchemaRegistry` 从 classpath 资源加载它们，并在加载时执行 INV-4 的启动断言：`maxSupportedVersion[N] >= 该能力已定义最高版本号`，不成立即 fail-fast。本阶段三个能力都只定义到 v1、上限声明为 1，因此断言平凡成立——**测试必须包含一条人为把上限设为 0 的用例来证明这个断言真的会响**，否则它是一条永远绿的假门。

`RuleDocument` 的字段集按 §2.1 落地：`ruleId`、`ruleVersion`、`dataLine`（**必填**，缺失即拒绝——`01-CONTEXT.md` §2.1 明确不引入「未分类」第四线，因为那会产生一条永不命中却看起来正常的规则）、`expression`、`failStrategy`（可选，缺省取注册项的默认值）、`deprecated`（只标记不改行为）、`removedIn`（**恒为 null**）。§2.2 明确 `deprecated` 只标记不改变行为：旧规则继续用、新规则也可继续写；填任何 `removedIn` 版本号都等于承认该版本删除了它，即破坏性变更，因此 schema 层直接拒绝非 null 值。

`DataLineRegistry` 承载 §2.1 的「可注册集合，SDK 不硬编码业务线」决策。注册项 `DataLineRegistration` 携带 `{name, defaultFailStrategy}`；**SDK 的 Java 代码里不得出现任何业务线名字符串**（`01-CONTEXT.md` §7 硬禁止，与 `PROJECT.md:5` 的通用性冲突）。注册表随版本管理，注册项从配置装配；未注册的数据线值可被推送（不是拒绝），但运行时标记为未识别并计入指标——这与「白名单外的 env 变量名使规则拒绝加载」（INV-10）是两条不同纪律，不要混用。启动时打印每条线实际生效的 fail 默认值（§2.1 明确要求）。

`RuleValidator` 按段执行三道，**任一道失败即该段整段拒绝**：
1. 内容哈希。`ContentHasher` 对段的规范化内容计算哈希，与文档中携带的哈希比对；不匹配即拒（GOV-10）。规范化必须确定（字段顺序无关），否则同一份内容两次推送会得出不同哈希。哈希算法用 JDK 内置的 SHA-256，不引三方库。
2. 结构与 schema 校验：字段缺失、类型不符、`dataLine` 缺失、`removedIn` 非 null、白名单外的变量名（该判定的输入来自 `01-04` 建立的 env 白名单，本任务以接口位接收）。
3. `RuleRelationValidator` 做段内与跨段关系约束：同一 `ruleId` 在段内重复出现、同 `ruleId` 的 `ruleVersion` 未递增、灰度段引用了限流段不存在的路由点。**关系校验失败同样导致整段拒绝，不做单条剔除**——`01-CONTEXT.md` §7「部分应用规则（单条丢弃 / 单条降级）」是硬禁止；INV-1 要求生效版本号与生效内容一一对应。

`RuleSetCompiler` 是「解析 + 校验 + 编译」的编排入口：拿到三段结果，**逐段**调用 `RuleValidator` 与 `RuleCompiler`，成功段产出可切换的编译产物，失败段产出「保留前一版本」的指令。`RuleCompiler` 把每条规则的 `expression` 交给 `01-02` 建立的静态闸门与编译入口，编译失败归入该段的整段拒绝。

`RuleValidatorTest`（GOV-06）断言段级原子拒绝：一条不合规规则导致**整段**不切换，段内其它合规规则也**不**生效；同时断言另两段不受牵连。
`AtomicityPartialFailureTest`（GOV-04）断言跨能力不连累，并额外断言「不存在部分字段生效」——具体做法是：先让 A 段成功生效并记录其版本与内容，再让 A 段推送一份部分不合规的文档，断言 A 段仍是**一字不差**的旧内容（逐字段比对，不是只比版本号）。
`ContentHashTest`（GOV-10）断言篡改必被拒：改动规则表达式中的一个字面量而保留原哈希，必须被拒且当前版本号不变。

`CapabilitySnapshot` 是单个能力段的不可变快照：持有该段 `ruleSetVersion`、`ruleId → CompiledRule` 的不可变映射、以及该段生效的 schema 版本。**构造后完全不可变**——所有集合在构造时拷贝为不可变视图，不留任何 setter 或可变集合字段访问器（OBS-03 的实现侧落点；其测试 `SnapshotImmutabilityTest` 由 `01-07` 提供，因为 VALIDATION 把该验证采样放在 wave 4）。

`SnapshotHolder` 按 §4 对 GOV-03 的修订：**每个能力段各自一个**不可变快照引用与各自的原子引用。切换一个段不影响另两个段的引用。读侧是**单次读**（一次原子读取引到局部变量，之后全程只用局部变量），不在读路径上反复读引用——这是 P99 预算的关键，`ARCHITECTURE.md` Hot-Path Cost Budget 一节把「多次 volatile 读」列为实际会咬人的成本之一。

`VersionGate` 实现 GOV-02 的单调性：每个能力段独立记账，只有**严格更大**的 `ruleSetVersion` 才被接受；更小或相等的推送被丢弃，且该段当前版本号**不变**。丢弃必须可观测（计数 + 日志），不允许静默——`01-CONTEXT.md` §7 禁止任何静默失效。§2.2 特别说明了为什么单调性必须按段而非按整份：全局单号会让跨团队发布互相踩踏，08:00 限流团队推 9 生效、08:05 缓存团队基于旧文档也填 9，被静默丢弃而控制台显示发布成功。

同时实现 **FND-09：决策路径零网络调用、无 TTL、无同步重试**。`SnapshotHolder` 与 `VersionGate` 在读路径上**不持有**任何外部依赖引用——不持有 `ConfigSource`、不持有 `RuleHistoryStore`、不持有定时器句柄。规则没有 TTL：`ARCHITECTURE.md` Anti-Pattern 3 记录了 TTL on rules 的反模式（规则应当是版本化的实体而不是会自己消失的缓存项）。规则历史写入**不在**决策路径上（`01-CONTEXT.md` §7 硬禁止，INV-6）。

三个接口的**签名冻结**（`01-CONTEXT.md` §6 开放项 5，§2.2 明确「Phase 1 冻结接口，不冻结实现」）：
- `SnapshotStore`：last-known-good 落盘的读写接口。实现属 `01-05`，此处只声明签名。
- `RuleHistoryStore`：append-only 规则历史，按 `(ruleId, ruleVersion)` 寻址，规模为 O(变更次数) 而非 O(实体数)。`RuleHistoryRecord` 携带生效的 schema 版本（§2.2 要求把生效的 schema 版本写入规则历史行）。
- `ConfigSource`：配置源接口。实现属 `01-06`（Nacos），此处不含任何 Nacos 类型。

`SnapshotAtomicityTest`（GOV-03 + FND-01 共享这一支验证命令）断言：N 个读线程与 M 个写线程并发跑，读侧任意时刻读到的段内容与版本号**自洽**（不出现「版本号是新版但内容是旧版」这种撕裂）；FND-01 的「可重入」在此落为「读侧不持有任何可变状态、连续读同一快照结果一致」。
