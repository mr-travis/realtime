`DecisionRecord` 的**九字段集被冻结**，字段清单直接取 `01-CONTEXT.md` INV-14（SEC-01）：`ruleId` / `ruleVersion` / `dataLine` / `decision` / `remaining` / `bucket` / `latencyUs` / `failStrategy` / `degraded`。**不得替换、不得增删、不得改名**——INV-14 是用户锁定的不变式，本计划不改写它，只把它变成编译期与测试期都强制的事实。

九个字段各自回答一个具体排障问题，且**没有一个字段承载原始业务数据**：

1. `ruleId`——命中了哪条规则（可追溯性的根，INV-1）。
2. `ruleVersion`——该规则的哪个版本。追溯靠 `(ruleId, ruleVersion)`，不靠把表达式复制进每一笔决策。
3. `dataLine`——哪条数据线（注册值，非硬编码字符串）。
4. `decision`——本次结论（`DecisionOutcome`：放行 / 拒绝 / 降级）。拒绝的具体原因并入 `decision` 的取值集（如 `REJECTED_QUOTA`、`REJECTED_FAIL_CLOSE`、`DEGRADED_LOCAL`），**不另设独立的原因字段**——INV-14 的九字段里没有它，新增即违反白名单。
5. `remaining`——配额余量，限流类决策的核心排障量。
6. `bucket`——命中的分桶标识（配额分桶/窗口档位）。
7. `latencyUs`——本次决策自身耗时（微秒），供 SDK 自身开销量化。
8. `failStrategy`——是否走了 fail 策略及走的哪一档（fail-close / fail-open / 规则覆写值）。
9. `degraded`——是否处于降级状态（`01-06` 的冷启动降级 / Nacos 不可达降级），使「按旧规则判定」在记录里直接可见。

`remaining` / `bucket` / `latencyUs` 三项在本阶段只有字段定义与非空语义，不要求有真实配额逻辑——限流实现属于后续阶段。本计划保证的是**字段存在、类型稳定、非空**：不适用时取显式缺省值而不是 `null`，否则记录对象出现可空字段，会破坏本记录的不可变断言。灰度/缓存类决策不涉及配额，`remaining` / `bucket` 同样取显式缺省值，且**缺省值必须可区分于真实值**——否则「剩余 0」会被误读成「配额耗尽」，这是本字段设计最容易埋下的误判。

**明确不进记录的东西**（INV-14 末句 + `01-CONTEXT.md` §7 硬禁止，OBS-02 的 Secure Behavior 就是「不携带原始入参 / key / 表达式」）：完整表达式文本、原始请求对象、原始卡号、原始 key、任何 PAN、traceId。排障时需要看表达式，去查 `RuleHistoryStore` 按 `(ruleId, ruleVersion)` 取——这就是为什么 INV-1 要求「生效版本号与生效内容一一对应」。这个取舍是本任务的核心，要在类 Javadoc 写明。

注意 INV-14 的九字段里**没有时间戳**：时间维度由承载决策记录的日志/追踪系统自己的接收时刻提供，SDK 不再重复存一次墙钟时刻。`latencyUs` 是**耗时**不是时刻——把 `System.currentTimeMillis()` 塞进 `latencyUs` 是极易犯的实现错误，这条要写进字段 Javadoc 并由测试断言其语义。

`Decision` 是一次决策的完整结果：不可变的 `DecisionRecord` 加一个**是否放行**的判定。业务代码读 `Decision`，可观测性读 `DecisionRecord`——这个分离让「取结论」不需要理解记录结构。

`DecisionRecordContractTest`（OBS-02）断言四组：(a) 字段集**恰好九个**，用反射读 declared fields 计数——这样将来有人加第十个字段时本测试会红，从而迫使改契约而不是随手加；(b) 九个字段的**名字集合与 INV-14 逐一相等**（改任一字段名即红），这条比只数个数更强：它挡住「把 `ruleVersion` 改名成 `version`」这类不改变数量却破坏契约的改动；(c) 九个字段的类型里不出现 `String` 之外的可变容器，也不出现任何能承载原始业务数据的类型；(d) 记录里**不出现**表达式文本——构造一条含特定标记串的表达式，确认该标记串在记录的全部可读字段（含 `toString`）中都不存在。(d) 是防止「顺手把表达式塞进一个字段」的真正防线，前三条挡不住它。另加一条 `latencyUs` 语义断言：它必须是**耗时**（同一进程内两次决策之间非负的差值量级），把墙钟时刻塞进去会让该断言的量级检查失败。

`RingBufferDecisionSink` 实现 `DecisionSink`，容量**固定且有界**（OBS-05）。实现要求：环形数组 + 原子游标，写入是**无锁**的（`compareAndSet` 推进写指针），读出是快照式。堆占用因此是「容量 × 记录大小」这个**编译期已知**的常量，与运行时长、决策量、实体数都无关——这就是 GOV-13 那个「不随规模增长」纪律在可观测性侧的对应物。

**满时丢弃，绝不阻塞业务线程**（OBS-06，`01-CONTEXT.md` §7 硬禁止）。这是本任务最容易做错的一处：写 ring buffer 最自然的实现是「满了就等」，或者更糟——「满了就调 `offer` 并在超时后阻塞」。两种都会把可观测性变成尾延迟来源。正确实现是：写指针推进失败即视为丢弃，**立即返回**。`SinkOverflowPolicy` 是显式策略枚举，本阶段**只**提供 `DROP_OLDEST` 与 `DROP_NEWEST` 两档（都不阻塞）；**不**提供任何带等待的档位——把「阻塞」做成一个可配置的选项，等于把事故变成一次配置改动。

`RingBufferStats` 暴露已写入、已覆盖、当前容量三项**可查询**状态。丢弃必须可观测（`01-CONTEXT.md` §7 禁止任何静默失效）：「记录在悄悄丢」如果不计数，运维看到的就是「可观测性数据断档」而无从判断是采集中断还是缓冲区满了。

`RingBufferOverflowTest`（OBS-06）用**延迟断言**证明不阻塞：单线程连续写入远超容量的记录，测量每次写入的耗时并断言其**上界**（如不超过某个宽松阈值）。这条断言要设得宽松——它防的是「阻塞」不是「慢」。另外断言丢弃计数恰好等于超出容量部分，不是大于等于。

`RingBufferSinkTest`（OBS-05）断言：容量固定；写入超过容量后读出的记录数恒等于容量；最旧的被覆盖、最新的保留（覆盖策略可配，两档各有断言）；并发多写者下不出现空洞或重复读出。

`DefaultMaskingPolicy` 是 **deny-by-default**（SEC-03）：未显式声明为「可明文」的字段，一律按掩码输出。这条纪律的方向与常见实现相反——常见做法是默认明文、白名单脱敏，而那意味着**新增一个字段时它默认是明文**，直到有人想起来加进白名单。deny-by-default 下新增字段默认是掩码，要明文必须显式声明，因此「漏加」的方向是安全的。`01-CONTEXT.md` §4 明确这条是用户在讨论中修订的语义：默认**脱敏**而非明文。

`MaskingContext` 是掩码的可查询封装：给定字段名返回掩码后的值，掩码结果对同一个输入**稳定**（同一卡号两次得到同一掩码，便于关联分析而不泄漏原文）。掩码算法用不可逆的摘要前若干位而非保留首尾若干位——保留首 6 尾 4 是 PCI 的常见做法，但那个格式仍然暴露了 BIN 与卡组织信息，而 BIN 本身在本项目里是要被路由的维度。取舍写在 Javadoc：本 SDK 默认不保留卡号任何位，只输出稳定摘要；如业务确需首尾保留，须显式配置且该配置本身进审计。

`DefaultMaskingTest`（SEC-03）断言：一个**从未声明过**的新字段名在默认策略下输出掩码而不是明文（这是 deny-by-default 的真正判据——用一个开发者没见过的字段名去试）；三类强敏感字段默认掩码；显式声明为可明文的字段才明文。
`MaskedContextTest`（SEC-02）断言：完整卡号 / CVV / 持卡人姓名三类在任何输出通道（含异常信息、debug 明细、`toString`）中都不以原文出现；debug 明细开关**默认关闭**；打开后输出的明细本身已脱敏（不是「打开就能看到明文」）。
`DebugGateIndependenceTest`（OBS-07）断言：把日志级别设为最严（等价于 debug 全部关闭）后，决策记录**照样产生并可读出**；决策记录的写入路径上不存在日志级别判断。实现上这条要求 `RingBufferDecisionSink` 不注入任何 logger，也不读任何日志开关——测试用「日志设施不可用」的场景（mock 一个永远不写任何东西的 logger）来证明它不依赖日志。这条与 `01-02` 的沙箱结论可查询性是同一族纪律：`01-CONTEXT.md` §7 禁止任何静默失效，可观测性不能被一个无关的开关关掉。
`SnapshotImmutabilityTest`（OBS-03）落在 `foundation-rule`，断言 `01-03` 产出的 `CapabilitySnapshot` 与 `RuleSetSnapshot` 构造后**无任何可变入口**：无 setter、无可变集合字段、无返回内部集合的 getter（返回的必须是不可变视图）；对反射可见的字段逐一取到非 null 值后再次读取同一快照，值不变；不存在任何方法能让调用方改到内部状态。`01-VALIDATION.md` 把本测试采样在 wave 4，本计划的执行 wave 4 与之一致；断言对象是 `01-03`（wave 3）的产出，本计划晚于它——由本计划创建该测试，避免与 `01-03` 产生同 wave 文件重叠。
