`DebouncedRuleApplier` 实现 GOV-07 的 `~200ms` 去抖。Nacos 批量发布会对同一份文档发来一串内容相同的回调；每收到一次就全量应用一次，会把一次发布放大成几十次编译 + 几十次原子切换。去抖的做法是：收到回调后重置一个 `~200ms` 计时窗，窗内的新回调只更新待应用的最新内容，窗静默后才真正应用一次。`~200ms` 是权衡值：太短去抖无效，太长会让「配置改了没生效」的观感变长；具体值标注待压测校准。

**乱序保护不靠去抖，靠 `01-03` 的 `VersionGate`**。这一点要分清：去抖解决「重复」，版本闸门解决「乱序」。Nacos 在网络抖动时可能先送达旧内容再送达新内容；如果去抖窗恰好把两次回调合并，窗内取「最后到达」就可能取到旧的。因此窗内必须按**内容版本号**保留并由 `VersionGate` 判定——取版本号最大的那次，而不是最后到达的那次。这条实现细节是本任务最容易做错的地方，也是 `01-05` 复用 `VersionGate` 的直接理由。

`ColdStartStrategy` 只有两档：`STRICT` 与 `RESILIENT`。`RESILIENT` 是 **opt-in**（FND-05）——`01-CONTEXT.md` §4 明确「新增配置一律 opt-in」，所以默认必须是 `STRICT`（配置不可达即启动失败），接入方显式声明才降级。

`ColdStartResolver` 的决策树是**二选一，没有第三条**（INV-5，`01-CONTEXT.md:90`；注意不是 INV-3——INV-3 是「schema 只加不减」，上一版误引）：
1. Nacos 可达且 schema 版本受支持 → 用 Nacos 首次拉取的规则。
2. Nacos 不可达但 `01-05` 的 last-known-good 可用且通过校验 → 用 LKG，并标记**降级状态**。`STRICT` 与 `RESILIENT` 在这一步**行为相同**。
3. 两者都不可用 → **按策略分岔**：`STRICT` 启动失败；`RESILIENT` 以空快照启动，但必须同时把 `foundation.rule.loaded=false` 与健康 **DOWN** 暴露出来。

`STRICT` 与 `RESILIENT` 的差别**只在第 3 步**（`01-CONTEXT.md` §4 记录用户在 RESILIENT 下的诉求是「明确显示降级状态」）。

**两路不可达必须可区分**（INV-5 第二子句：`01-CONTEXT.md:90` 明文要求「日志与健康端点须区分「配置中心不可达」与「MySQL 规则历史不可达」」；`01-RESEARCH.md:950` V7 重申）。冷启动要读的是**两路**来源：配置中心（Nacos，`ConfigSource`）与 MySQL 规则历史（`01-03` 冻结的 `RuleHistoryStore`，LKG 从这里取）。两路都可能是不可达的，而它们的**故障含义与处置完全不同**——Nacos 不可达是「最新规则拿不到」，MySQL 不可达是「连上次的规则都取不到」；后者意味着连 `STRICT` 的 LKG 分支都无法成立。因此 `ColdStartOutcome` 携带**原因分类枚举** `ColdStartCause`：

- `NONE`——启动成功且规则来自配置中心。
- `CONFIG_UNREACHABLE`——Nacos 不可达（`01-RESEARCH.md:559` 已把该值列入 `foundation.degraded{mode,cause}` 的 `cause` 取值域，指标与日志共用同一套取值）。
- `HISTORY_UNREACHABLE`——MySQL `RuleHistoryStore` 不可达。
- `BOTH_UNREACHABLE`——两路都不可达（`STRICT` 启动失败、`RESILIENT` 空快照启动的唯一情形）。

`ColdStartCause` 必须同时出现在**日志字段**与**健康端点**响应体中，且两处取值来自同一枚举——不允许日志写一种字符串、健康端点写另一种，那会让运维在排障时无法把两者对上。健康端点另带 `cause` 维度，指标侧对应 `foundation.degraded{mode,cause}`（`01-08` Task 1 的 `DecisionOutcomeCounters` / 降级计数不合并该 cause 取值）。`StartupFailureTest` 必须断言这四类原因**两两可区分**，尤其是 `CONFIG_UNREACHABLE` 与 `HISTORY_UNREACHABLE` 不得互相折叠——它们折叠成一个 `UNREACHABLE` 值，就等于没做这条要求。

**冷启动重试的边界**（`01-CONTEXT.md:151` §6 开放项 7 要求「`Nacos` 与 `MySQL` **各自**」的重试上限与最终失败行为；依据 `01-RESEARCH.md:537-542` D.7：最大 **5** 次、总预算 **30s**、退避 **1 / 2 / 4 / 8 / 16s**）：重试在**每一路内独立进行**，Nacos 的 5 次不与 MySQL 的 5 次共享预算（串行相加可能逼近 60s，超出 30s 总预算的意图），实现上把总预算按路各给 30s 并**并发**发起两路探测，而不是串行等待——串行会让「Nacos 卡 30s + MySQL 卡 30s」变成 60s 冷启动，这正是本条要避免的。退避序列封顶在 16s：第 5 次之后还有 16s 等待，第 6 次已无意义，故次数硬停在 5。**次数与总预算冲突时以墙钟预算为准**——名义退避 `1+2+4+8+16 = 31s` 比 `total-budget` 的 30s 多 1s，这个 1s 的差额必须由实现消解而不是靠文档含糊过去：第 5 次退避的名义值 16s 被**截断为 `total_budget - 已耗时间`**（15s），使累计恰好落在 30s。每次尝试本身也要受剩余预算约束：若剩余时间短于该次尝试的超时，则**不再重试**，直接按 `fail-strategy` 走 `STRICT` / `RESILIENT` 分岔。截断必须是可观测的（`ColdStartOutcome` 记 `budget_truncated=true`），否则一次「实际只等了 15s」的重试在日志里会被误读成 16s。某一路重试耗尽后的**最终失败行为**按 `ColdStartStrategy` 分岔，与上面的决策树第 3 步一致：`STRICT` 启动失败并带 cause，`RESILIENT` 空快照启动、`loaded=false`、健康 DOWN、并带 cause。重试只发生在**冷启动路径**上——运行期决策路径零网络调用（INV-6 / FND-09，`01-03` 已用 `NoNetworkOnDecisionPathTest` 钉住），这两条不冲突，但执行者不得把重试器挂到任何决策路径上。

**这里最容易搞错的是把「无规则」与「静默无规则」混为一谈。** 本任务真正的不变式是 `01-CONTEXT.md` §7 与 ROADMAP 成功标准 2 说的那句——**「无规则」绝不静默**，而不是「任何时候都不许没有规则」。`RESILIENT` 允许在无 LKG 时启动，但这个「无规则」状态必须**三点齐全**才算合法：`foundation.rule.loaded=false`、健康 **DOWN**、`ColdStartOutcome` 可查询。任何一点缺失就是 §7 禁止的静默失效。`STRICT` 则连这三点都不给，直接启动失败——它的立场是「宁可起不来，也不要在调用方不知情的情况下没有限流」。

所以「两者都不允许静默无规则运行」成立，而「两者都不允许无规则运行」**不成立**：后者会把 `RESILIENT` 压成 `STRICT` 的同义词，这个策略档位就没有存在意义了。降级状态必须可查询（`ColdStartOutcome`），不只打日志。

冷启动策略作为 `ColdStartStrategy` 枚举从 SDK API 参数传入，**不在本模块读配置**。`01-01` 拥有 `foundation.*` 属性面，`01-06` 不反向依赖它——这样 `01-01`（wave 1）不需要知道后续模块的类型。

`RuleChangeListenerTest`（GOV-07）断言：(a) `~200ms` 内的 10 次重复回调只应用**一次**（用计数器断言，不是靠观察最终状态）；(b) 乱序回调（先版本 11、后版本 10）后生效的是 11；(c) 每次应用都经过 `VersionGate`，不旁路——用 mock 验证闸门被调用。
`StartupFailureTest`（FND-05）断言：(a) 默认策略是 `STRICT`（不是 RESILIENT）；(b) `STRICT` + Nacos 不可达 + 无 LKG → 启动失败；(c) `STRICT` + Nacos 不可达 + 有有效 LKG → 启动成功且降级状态可查询（与 RESILIENT 同）；(d) `RESILIENT` + Nacos 不可达 + 无 LKG → **启动成功但状态全显**：`foundation.rule.loaded=false`、健康 **DOWN**、`ColdStartOutcome` 报告未加载，三点逐个断言；(e) 降级状态可从 `ColdStartOutcome` 读到，不只出现在日志；**(f) 原因分类可区分（INV-5 第二子句）**：仅 Nacos 不可达 → `ColdStartCause.CONFIG_UNREACHABLE`；仅 MySQL `RuleHistoryStore` 不可达 → `HISTORY_UNREACHABLE`；两路都不可达 → `BOTH_UNREACHABLE`；成功 → `NONE`，四类**两两可区分**且不得互相折叠（把前两者折叠成同一个 `UNREACHABLE` 值此用例即失败）；**(g) cause 同时出现在日志字段与健康端点响应体**，且两处取值来自同一枚举（断言两者相等，防止日志与健康端点各写一种字符串）；**(h) 重试边界**：`ColdStartRetryPolicy` 的最大尝试次数为 5、退避序列为 1/2/4/8/16 秒、总预算 30 秒，且 Nacos 与 MySQL **各自**独立计数（断言一路耗尽不影响另一路的重试次数）；**(i) 重试只在冷启动路径**——用 mock 验证 N 次决策后配置中心与规则历史客户端**零交互**（与 `01-03` 的 `NoNetworkOnDecisionPathTest` 同一纪律，防止重试器被误挂到决策路径）。
