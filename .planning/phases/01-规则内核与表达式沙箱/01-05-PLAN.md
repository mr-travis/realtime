`LastKnownGoodStore` 实现 `01-03` 冻结的 `SnapshotStore` 接口。**落盘走 temp-file + `ATOMIC_MOVE`**（GOV-05）：

写入序列固定为：写同目录临时文件 → `fsync` → `ATOMIC_MOVE` 覆盖目标 → 清理残留临时文件。同目录是硬要求——跨文件系统的 `ATOMIC_MOVE` 会失败。`fsync` 必须在 move 之前，否则崩溃后可能出现「文件名已换、内容未落盘」的空洞。

**落盘路径的唯一来源是运维配置，不是规则内容**（`01-RESEARCH.md` Prohibitions #5「规则用 `-` 指定隐藏资源」的处置）：快照目录来自 `foundation.*` 配置项，写入目标是该目录下一个**固定文件名**，规则集里的任何字段（能力段名、`ruleSetVersion`、条目 key、表达式）都**不得**参与路径拼接。因此 Phase 1 不存在规则内容驱动的路径逃逸面，`path.normalize().startsWith(base)` 这道防护在本阶段**无可保护的输入**——不写这个断言不是遗漏。保留这条说明是为了让后续阶段（规则可指定资源位置时）必须重新评估，而不是让本阶段的读者以为漏了一道校验。

**恢复必须复用 `01-03` 的 `VersionGate`**。这是本任务最容易被做错的一处：如果恢复路径自己写一份版本判定，它与推送路径的判定迟早分歧，表现为「重启后 LKG 版本比 Nacos 里的当前版本旧，但 SDK 不知道该怎么处理」。复用同一个闸门意味着：恢复出来的快照走与推送完全相同的单调性与按段语义。

**恢复出的快照必须重新过校验**（`01-03` 的 `RuleValidator`），不能因为「它是我自己写的」就免检——磁盘内容可能被截断、被外部改写、或来自旧版本 SDK 的格式。这条与 `01-CONTEXT.md` §7 的内容哈希纪律一致。

`SnapshotSerializer` 的输出必须是**确定性**的：同样的快照状态序列化两次得到同样的字节。确定性是 `01-03` 内容哈希能跨重启成立的前提。序列化用 Jackson（Boot BOM 管理，JDK 8 兼容），不引三方序列化框架。

**INV-5 的落点**（`01-CONTEXT.md:90`；上一版误标为 INV-3——INV-3 是「schema 只加不减」，与冷启动无关）：冷启动的决策是二选一——读到并通过校验的 LKG，或硬失败。**不存在**「读不到就用内置默认继续跑」这条路径。`LastKnownGoodStore` 在读不到可用快照时抛出专门的异常，由 `01-06` 的冷启动策略（`STRICT` / `RESILIENT`）决定是 fail-fast 还是走 Nacos 首次拉取——但「无规则继续跑」在任何模式下都不允许（§4 已明确用户在 RESILIENT 下的诉求是「明确显示降级状态」，不是「静默无规则」）。

`SnapshotDirWatchdog` 定期探针快照目录的可写性（GOV-12）。这条需求来自一个具体的失败模式：容器挂载、磁盘满、权限变更都会让目录突然不可写，而 LKG 落盘失败往往**发生在最坏的时刻**——配置刚被推送、新快照正要落盘。如果只有落盘时才失败，运维看到的是「限流突然开始按旧规则判定」而没有任何前置信号。

探针做的事很小：周期性写一个临时探针文件并删除，读出可写 / 不可写 / 磁盘占用超阈值三种状态。周期可配。`SnapshotDirStatus` 是可查询的状态值对象——`01-CONTEXT.md` §7 禁止任何静默失效，因此状态必须是**可查询**的，不只写日志。

探针与落盘**用同一套可观测信号**：`TempFileAtomicWriter` 的写入前检查直接复用 `SnapshotDirStatus`，避免「探针说可写、落盘说不可写」的两套真相。探针发现不可写时**不阻止**正在服务的决策路径（决策路径读的是内存快照，与目录无关），只标记降级状态并计入可观测信号——这一点要说清，否则容易被误读成「目录不可写就该停止决策」。

探针线程是**后台守护线程**，不阻塞决策路径；探针自身失败不抛出到调用方（它只有一种输出：状态值 + 计数）。这是本模块里唯一允许「内部异常被自己消化」的地方，理由是探针没有调用方需要通知，状态值已经承载了全部信息——Javadoc 必须写明这个例外及理由，避免被当成反例。

`RouteTable` 的核心不变式：**条目数等于规则数，不等于卡片数**（GOV-13）。路由表是「规则的路由表」，不是「卡片的表」。卡片维度的东西放在 `CardRouteIndex`——它按前缀分段（BIN 段）组织，**有界**且与运行期遇到的卡片数脱钩：`CardRouteIndex` 只存路由点级别的映射，不为每张见过的卡建条目。这条区分是 GOV-13 的全部要点，`01-VALIDATION.md` 的人工验证项也点名要确认「路由表条目数 == 规则数且不随运行时长增长」。

`RoutePlanDiffer` 实现差量替换（GOV-15）。它对比新旧两个 `RoutePlan`，只重编译 `ruleId` 与内容**都**变化（或新增）的规则，未变的编译产物直接复用。这条需求背后的真实问题是 P99：整份规则集重编译会在切换瞬间叠加为一次计算尖刺，而 `PROJECT.md` 把「规则刷新不得叠加为 p99 尖刺」列为硬约束。差量替换把切换成本从 O(全部规则) 降到 O(变化规则)。

差量的判定依据是**内容哈希**（`01-03` 的 `ContentHasher`），不是文本相等——文本相等要多一次 O(长度) 比较，而哈希已经在解析时算过。复用同一份哈希值而不是重算，是这条实现的关键细节。

`RuleHistoryAppender` 把 append-only 规则历史写入放在**切换路径**上，不在决策路径上（`01-CONTEXT.md` §7 硬禁止，INV-6）。`01-03` 冻结的 `RuleHistoryStore` 接口在这里获得一个实现：追加 `(ruleId, ruleVersion, 生效的 schema 版本, 时间戳)`。写入**失败不回滚**切换——历史是审计线索，不是生效前提；失败必须可观测（计数 + 日志）。这条取舍要写进 Javadoc：决策正确性优先于审计完整性，审计缺口由可观测信号暴露而不是由同步写阻塞服务。

`RoutePlanSizeTest`（GOV-13，**INV-13** = 路由表大小 == 已编写规则数，`01-CONTEXT.md:98`）断言：构造 10 万卡 BIN 量级的输入后，`RouteTable` 条目数**恒等于规则数**；`CardRouteIndex` 的条目数随 BIN 段数增长而**不随卡片数增长**（这是本测试的核心断言，不能只查 RouteTable）；连续跑多轮「模拟不同卡片到来」后两个结构的条目数均不变。
`RoutePlanDiffTest`（GOV-15）断言：新旧规则集只有一条规则变化时，该规则被重编译、未变规则的编译产物是**同一实例**（不是等价的新实例）；无变化时差量为空且不触发任何重编译。
  </action>
