## 2. 四个决策区（含被否项，避免规划时重复论证）

### 2.1 数据线在规则 schema 中怎么表达

- **规则级字段**，单份规则集内声明，运行时按入参 `dataLine` 路由。`dataLine` 来自入参而非规则本身，故只能是路由键。
- **可注册集合，SDK 不硬编码业务线**（Q2 由「SDK 内置固定枚举」**反转**而来——出示 `PROJECT.md:5`「本子应用对它们是通用的，不绑定具体业务场景」后用户改选）。未注册值可推送，运行时标记未识别并计入指标。
- **必填，缺失即拒绝**（粒度按 2.2 的结论为按能力段）。不引入「未分类」第四线——那会产生一条永不命中却看起来正常的规则。
- **fail 默认值随注册项走**：注册项携带 `{name, defaultFailStrategy}`。启动时打印每条线实际生效的默认值。
- **被否**：SDK 内置固定枚举（逼出「缺值」态 + 新增业务线要改 SDK 发版）；数据线级分区（每线一份规则集 → 为每条线复制全部规则，违反 GOV-13）。

### 2.2 schema 版本号策略与演进规则

- **`schemaVersion` 按能力分列**（限流/灰度/缓存各一条版本线）。被否：全局单一整数（演进互相阻塞）、内容哈希（无法表达「哪个形状」，撑不起 409 `SCHEMA_INCOMPATIBLE`）。
- **`ruleSetVersion` 按能力分号**（关键修正）。原「全局单号」会导致跨团队发布互相踩踏：08:00 限流团队推 9 生效，08:05 缓存团队基于旧文档也填 9 推送，按 GOV-02「更小或相等被丢弃」被静默丢弃，而控制台显示「发布成功」。
- **`ruleVersion` 每规则独立递增**，仅该规则自身内容变化时递增——「规则 42 版本 7→8」必须等于它真的改过一次，这是项目核心价值的审计语义。
- **规则集文档按能力分区段**：`{rateLimit:{version,rules[]}, cache:{version,rules[]}, canary:{version,rules[]}}`。发布通道只写被改动的段，陈旧段不进本次推送；Nacos 推的是整份文档，**拼回未改动段的合并责任在发布通道，SDK 侧不做合并**。
- **schema 演进「只加不减」**：仅允许新增可选字段与新增枚举值；删字段、改类型、改必填性一律不兼容。因 `dataLine` 已定为开放注册集合（不进 schema），**新增一条业务线不 bump schema 版本**；「新增枚举值」指 SDK 自有枚举（`failStrategy` 取值、决策类型、规则类型）。
- **schema 版本号来源**：独立定义文件（每能力一个，版本内**完整**声明，如 `rate-limit/v1.json`），与 SDK 制品版本**解耦**。纯 bugfix 不 bump schema 版本——否则一个空指针修复会把 schema 顶高，升级窗口内全量实例停用新规则。
- **上限声明**：`schemas/<capability>.support` 资源文件（`{"maxSupportedVersion": N}`），与定义文件同目录使「定义到第几版、支持到第几版」同屏可对。**不得**放在代码常量（跨能力汇总需人工 review）或 Spring 配置/Nacos（会把编译期事实变成运行时可变量，下调上限即自伤）。
- **段内不声明 `schemaVersion`**：段里的 `version` 是推送序号。SDK 始终按 `maxSchemaVersion[N]` 校验（「只加不减」保证 v1 规则在 v2 下必然合法），并把生效的 schema 版本写入 MySQL 规则历史行。
- **旧 SDK 收到更高 schema**：整份原子拒绝 + 保留 last-known-good + 计数。滚动升级期间新旧实例规则集版本可能不一致（各自内部一致）。
- **`deprecated` 只标记不改变行为**：旧规则继续用、新规则也可继续写；`removedIn` 恒为 `null`（填任何版本号都等于承认 vN 删除它，即破坏性变更）。代价：schema 文件单调增长，已明确接受，换取「任何时刻可按旧规则原样重放」的回滚前提。
- **规则历史 append-only 永不删**，按 `(ruleId, ruleVersion)` 寻址；决策记录只带 `ruleId+ruleVersion`，九字段不膨胀。规模为 O(变更次数) 而非 O(实体数)。
- **存储可切换**：规则历史存储与配置源均置于 SDK 自有接口之后（`RuleHistoryStore` / `ConfigSource`），MySQL 与 Nacos 各为一个实现，由配置选择。MySQL 为默认（结构化查询更清晰）。**Phase 1 冻结接口，不冻结实现。**
- **被否**：扁平列表逐段判版本（陈旧段丢弃 + 新版段生效 = 部分生效，撞 GOV-04）；每能力每版本一个文件 + 增量（单文件不完整，且增量结构无法表达「可选变必填」）；跟制品版本绑定；内容哈希；滚动清理历史；决策记录内联摘要。

### 2.3 表达式可读的环境变量契约

- **变量集合 SDK 侧固定，按能力分**，规则**不声明任何变量**。暴露面最小且可在代码里穷举审计；结构上不可能出现「规则声明了 SDK 不提供的变量」。代价：加变量要发 SDK 版本，需同步改三处（能力定义、变量集、启动断言）。
- **原始字段进 env，派生全在表达式**。阈值、分档、组合条件写在表达式里随配置表下发，调阈值不发 SDK 版本。**显式禁止提供任何中间档位变量**——`amountTear == 'T_10K_PLUS'` 这类自由字符串名拼错后恒为 false 且不报错，是项目一贯拒绝的静默失效点。原始值直取 `amount > 10000` 中字面量即边界，可直接审计。
- **`amount` 取 `long`、单位分**（避开浮点误差；装箱比 `BigDecimal` 轻）。单位约定在 SDK 固定集定义处定死，全库单点。
- **字段候选集**（最终清单留规划逐条确认）：

  | 能力 | 字段 |
  |---|---|
  | `RATE_LIMIT` | `amount`(long/分)、`channel`、`dataLine`、`cardBin`(明文非敏感)、`cardProduct`、`issuerId`、`merchantId` |
  | `CANARY` | `subjectHash`(主体标识哈希，永不传原文)、`cardProduct`、`issuerId`、`channel`、`dataLine` |
  | `CACHE` | `keyHash`(`sensitive=true` 时唯一可进的 key 形态)、`entryType`(额度/账户/配置)、`dataLine` |

- **敏感字段三层分级**：①公开（`channel`/`cardProduct`/`dataLine`/`cardBin`）明文进 env；②业务标识（`merchantId`/`issuerId`/`subjectHash`/`keyHash`）明文进 env 但**禁止做指标标签**（Out of Scope 第 10 条）；③**强敏感（完整卡号、CVV、持卡人姓名）永不进 env**。第三层靠代码里硬性划掉，不靠运行时拦截。
- **取值方式：反射 + 递归展开 + 白名单**（用户选定，已告知风险后被接受）。业务代码无需逐字段构造 context。
- **白名单是唯一屏障**（deny-by-default）：不在白名单的 key 使该规则判为不合规并**拒绝加载**，同时计数告警。
- **变量缺失 → nil → 不命中 + 独立计数**：与既有 `CAN-09`（targeting key 缺失 fail-open 到「不匹配」并计指标）同构。规则作者可自行写守卫（`issuerId != nil && ...`）。
- **被否**：规则侧声明 `exposedVars`（变量集不在代码里，且需检出「声明了 SDK 不提供的变量」）；全局单一固定集（暴露面最大，限流规则能读到灰度专用 `userHash`）；只放预分档值（调阈值要发版 + 可拼错的档位名）；不反射的显式 context（样板代码，但为原推荐项）。

### 2.4 沙箱逃逸的处置粒度

- **沙箱拦截（编译期）→ 按能力段整段拒绝**。逃逸企图在 `validate()`/`compile()` 即被拦下（Aviator 5.4.4 沙箱关闭 `Module`/`NewInstance`/`InternalVars`/`StaticFields`/`StaticMethods` 与反射，设循环与步数上限），属加载期可判定事件，与 Area 2 的「载荷结构错误 → 按能力段原子拒绝」同一档。
- **决定性理由**：不是可用性，而是**版本审计能否自圆其说**。只丢单条或降级恒不命中都会让段版本号成为二选一——算新号则「已生效」不等于推送内容，算旧号则内容已变而版本未动。部分应用从根上破坏「生效版本号 ↔ 生效内容一一对应」。
- **运行期求值失败（nil 运算 / 类型不匹配 / 步数耗尽）→ 走 fail 策略，段不回滚**。复用 `RL-17`（限流 fail-close）/ `CAN-06`（灰度 fail-open）；`RL-20` 要求 fail-open 时必须有独立静态本地回退配额兜底（不得等于无限通行）；`RL-21` 要求实际生效的 `failStrategy` 记入 `DecisionRecord`。**不许回滚停服**（会把瞬时异常放大成整个能力不可用），**不许按未命中处理**（静默失效）。
- **逃逸企图与成功统一为 `sandbox_violation` 单一指标，边界划到 SDK 外**。**逃逸成功在 SDK 内不可检测**——沙箱被绕过时表达式编译通过、求值通过、返回一个值，攻击者的 `Runtime.exec()` 在 SDK 眼里就是一个 boolean。成功检测属进程外（EDR / 子进程与出网监控）。**SDK 契约不得暗示具备逃逸成功检测能力。**
- **企图不升级为高危安全告警**：规则作者试错、拷贝外部代码都会触发编译期拦截；全部走高危通道会在数月内被无视，真事件与噪声混同。

## 3. 不可动摇的不变量

规划与实现均不得违反。违反即为缺陷，不是权衡。

| # | 不变量 |
|---|---|
| INV-1 | 生效版本号 ↔ 生效内容**一一对应**；禁止部分应用（一项规则不合规即该能力段整段不切换） |
| INV-2 | 原子切换、版本单调性、schema 校验**均按能力段**；跨能力互不连累 |
| INV-3 | schema **只加不减**：`deprecated` 字段永不删除、永不改类型、永不改必填性；`removedIn` 恒为 `null` |
| INV-4 | 启动断言必须成立：`maxSchemaVersion[N] >= 该能力已定义最高版本号`，否则 **fail-fast**，不得降级为运行期拒绝 |
| INV-5 | 冷启动无 last-known-good 且配置中心/规则历史不可达 → **进程启动失败**；日志与健康端点须区分「配置中心不可达」与「MySQL 规则历史不可达」 |
| INV-6 | 运行期决策路径**零网络调用**（单节点模式零网络调用是硬约束） |
| INV-7 | env 变量集 **SDK 侧固定、按能力分**；规则不声明变量 |
| INV-8 | **强敏感字段（完整卡号 / CVV / 持卡人姓名）永不进 env**；由 deny-by-default 白名单在代码层保证 |
| INV-9 | 不提供任何**中间档位变量**（消除可拼错且不报错的自由字符串名） |
| INV-10 | 白名单外的 key 使规则**拒绝加载**，不是忽略 |
| INV-11 | 「因变量缺失未命中」与「表达式评估为 false」是**两个独立指标**，可按 `ruleId` 下钻 |
| INV-12 | 「因求值失败按 fail 策略返回」与上一条也是独立指标 |
| INV-13 | 路由表大小 == 已编写规则数，不随运行时长或实体数增长（GOV-13） |
| INV-14 | `DecisionRecord` 字段白名单在 SDK 层强制（SEC-01）：仅 `ruleId`/`ruleVersion`/`dataLine`/`decision`/`remaining`/`bucket`/`latencyUs`/`failStrategy`/`degraded`；禁止原始入参、原始 key、完整表达式文本 |
| INV-15 | 逃逸成功检测**不在 SDK 职责内**；SDK 只上报可观测的逃逸企图，契约不得暗示更多 |

## 6. 留到规划阶段逐条确认的开放项

以下**不需要再问用户**，是规划必须自行设计并落成任务的内容：

1. 每条能力 env 变量集的**最终字段清单与类型**（`amount`=long/分已定，其余逐条确认）。
2. 每条能力变量集大小的**上限**，并纳入 `EXPR-04` JMH 基准。
3. **反射实现细节**：深度上限、集合/`Map` 展开策略、循环引用保护、反射元数据缓存结构（不缓存必击穿 P99）。
4. **白名单的承载形态**：代码常量 / 注解 / 配置，以及它如何与启动断言联动。
5. `RuleHistoryStore` / `ConfigSource` 的**接口签名冻结**（不冻结实现）。
6. schema 定义文件与 `.support` 文件的**具体形态**（目录布局、字段声明格式）。
7. **冷启动重试上限**与最终失败行为（Nacos 与 MySQL 各自）。
8. 各独立计数器的**名称与维度**，以及与 meter 契约的对应。
9. 发布通道的**段合并逻辑**归属与实现位置（SDK 侧不做合并）。
10. `sandbox_violation` 指标与其他失败分类计数器的**命名与聚合边界**。

## 7. 禁止事项（反模式）

| 禁止 | 原因 |
|---|---|
| 新增任何中间档位变量（`amountTier` 等） | 自由字符串名拼错后恒为 false 且不报错（INV-9） |
| 部分应用规则（单条丢弃 / 单条降级） | 破坏「版本号 ↔ 内容」一一对应（INV-1） |
| 在 SDK Java 代码中硬编码业务线名 | 与 `PROJECT.md:5` 通用性冲突（Area 1 Q2/Q4） |
| 在 SDK 内实现"逃逸成功检测" | SDK 内无信号，只会产出高误报（INV-15） |
| 用异常做热路径控制流 | 与 P99 < 10µs 预算相冲 |
| 任何静默失效 | 每类失败必须有独立、可下钻的计数（INV-11/12） |
| 把 `maxSchemaVersion` 做成运行时可变量 | 下调上限即让全量实例对已生效规则集整份拒绝（自伤） |
| 让 SDK 侧做段合并 | Nacos 推整份文档，合并是发布通道责任（Area 2 F2） |
| 把规则历史写入放在决策路径上 | 违反 INV-6 |
